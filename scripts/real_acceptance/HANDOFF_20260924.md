## 2. 原启动链及重要事实

### XML 与 Python 是两套入口

- Python：`scripts/run_competition.sh`、`competition_launch.py`、`competition_controller.py`。默认 slam=True，延迟 10s 后启动控制器；控制器 INIT 等地图、map/base_footprint TF 和 action，再等5s，然后开启云台扫描。
- XML：`pb2025_sentry_behavior_reality_launch.py` 只启动行为树 server/client；`sentry_behavior_reality.yaml` 指定 target_tree=rmul_2025_reality。Nav2 另外启动。
- `rmul_2025_reality.xml` 主树原先先执行 gimbal_init，随后才 check_game_start。gimbal_init 只发布 0.5 rad/s 扫描、等待、打印，无电机校零或坐标初始化。
- XML 的 duration=13000 是先发指令再等待，不能当作启动前延迟。比赛条件之后还会先发 cmd_spin=7.0，再导航。保护应阻止整棵目标树提前启动。
- 本轮没有改 XML、Python competition 方案及 XML 航点。

### 生产导航模式尚未替换

- `rm_navigation_reality_launch.py` 包含 `bringup_launch.py`。
- slam=True 进入 `slam_launch.py`，启动 Point-LIO + slam_toolbox，并另外发静态 map/odom，默认 x=.7 y=.5 yaw=0。
- reality/nav2_params.yaml 的 slam_toolbox 仍有 transform_publish_period=0.0、use_scan_matching=false、do_loop_closing=false。这些尚未修正。
- slam=False 进入 `localization_launch.py`，仍是 map_server + small_gicp；尚未改为生产 AMCL。
- small_gicp 以 previous_result_t_ 为单一初值做 GICP，失败只警告，不是未知起点搜索。其 robot_base_frame=gimbal_yaw，配置初始姿态按云台参考系解释。
- ros2_services.yaml 中旧 XML 正赛服务配套 slam=False，但相关服务段是注释，不能据此声称机器当前运行哪种入口。
- map YAML 的栅格 origin 不等于 map/odom TF，旧 .7/.5 静态偏置与 slam_toolbox 生成地图的原点可能不一致。替换后须保持唯一 map/odom 发布者，不能同时跑静态 TF、GICP、AMCL。

### 真机几何不能照搬上游模型

已保存在 `scripts/real_acceptance/README.md` 的现场确认：MID360 **随云台 yaw 转动**，上游 SDF 却挂在 chassis。早期对话仅看模型所得“雷达固定在底盘”的判断已被现场资料纠正。

- 验收 static_launch.py 原来用 URDF 后处理折叠两个虚拟云台关节、将雷达挂到 gimbal_yaw，并由 yaw_feedback.py 从域0读取真实 LK 编码器，向域88发 JointState。这是已有且经过部分实车验证的修正，本轮将其复用到生产。
- 上游 joint_state_publisher 可能用默认0角假装有反馈；实车生产应使用测量值，不造默认关节。
- Hub 导航入口对平移 x/y 取负。已有验收 navigation_trial.py 在发给 Hub 前再取负适配。生产 fake_vel_transform 原先没适配，因此存在反向。
- `ChassisController::gimbal_yaw_angle()` getter 本身返回负的内部角度，Hub 使用 R(-theta) 后实际方向是 R(+encoder_angle)。不能“顺手修正”该 getter 的负号。
- 现有遥控、急停、Hub仲裁逻辑不得改变。
